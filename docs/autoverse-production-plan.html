00

How to read this document

Document 01 answered what Autoverse is and in what order we build it. The Model Delivery Spec defines how finished 3D models are handed into the system. This document answers the remaining question: what makes it safe to run in production for paying clients — and it is the strictest of the set. It governs the engine (hosting, structured asset storage, data, security, leads, content, webhooks) and every application built on it: the configurator, digital brochure, virtual showroom, brand dashboard, and admin portal now; the Autoverse consumer platform and any later app inherit the same contract.

The vision, the five surfaces, the configurator model, the tech stack and the phase order from v1.0 all stand unchanged. What changes is the standard applied to each: v1.0 said we will test, log, and gate. This document defines exactly what that means, makes each one blocking, and specifies the proof.

The rule that governs this document

A guarantee without a mechanism is a wish. A mechanism without a test is a rumour. Nothing enters this plan unless it can be enforced by construction and demonstrated on demand. Where something cannot yet be proven, it is written down as a risk in §20 rather than assumed away.

Blocking means the pipeline stops. Tracked means it is measured and reviewed, but does not stop a release.

01

The production doctrine

Five non-negotiables. Every section that follows exists to serve one of them.

01

The pipeline is never broken

Main is always deployable. A red build is the highest-priority work in the company — no new feature work starts while the pipeline is red.

02

A feature is working or it does not exist

Shipped-but-broken is worse than absent. Everything reaches users through a flag, and every flag has a verified kill path.

03

Nothing happens unobserved

Every request, job, event and failure emits a structured, correlated log. If we cannot reconstruct what happened from telemetry alone, the feature is not done.

04

Failure is contained, never total

Every external dependency has a timeout, a retry policy, and a defined degraded mode. One dependency failing must never take the page down.

05

No flow is missed

Every business-critical flow is inventoried, end-to-end tested, and monitored in production. Data loss is treated as a severity-one incident.

06

Tenant isolation is absolute

No brand can ever see another brand's data. Enforced at the database, proven by mandatory tests, and re-proven on every schema change.

Standing priority — amended

v1.0 ranked ship speed → premium feel → scalable architecture. That still holds for design decisions. It does not hold against this doctrine: correctness, isolation and observability outrank ship speed, always. We cut scope to go faster. We never cut gates.

3.1 Boundary rules Blocking

  • The iframe never touches data. No Supabase key of any kind reaches the render surface. It receives commands and emits signals — nothing else.
  • Browsers never write directly to tables. All writes from consumer surfaces route through an Edge Function that validates, rate-limits, and stamps provenance.
  • The service role key exists in exactly two places: CI migration runs and server-side jobs. It is never present in any browser bundle, mobile binary, or Edge Function reachable by an anonymous caller.
  • No component queries the database. Data access flows through a typed layer with one owner per entity.
  • Every cross-boundary payload is validated at the boundary with a schema (Zod), on both sides — inbound and outbound.
  • The render farm is reached only through the job queue and the bucket. The engine writes a job, the farm writes frames; farm hardware holds nothing beyond a scoped bucket write key, so the serving platform never depends on a workstation being reachable.
  • The AI generation provider receives renders and prompts — never PII, never lead data. Its output enters the system only through the approval state machine.
  • Assets are immutable once written: content-hashed paths, checksums recorded at upload, re-renders create new versions rather than overwriting.
04

Tenancy & data integrity

Row-level security remains the keystone: one mechanism delivering multi-tenancy, RBAC and confidentiality at the layer no application bug can bypass. This section makes it un-skippable.

4.1 The RLS discipline Blocking

  • Every table carrying brand-scoped data has brand_id and an RLS policy created in the same migration. A migration adding a table without a policy fails review automatically.
  • Deny by default. Policies grant; nothing is open unless granted. New tables start with RLS enabled and no permissive policy.
  • Every policy ships with a paired isolation test: as brand A, attempt read/write on brand B's rows; assert failure. These tests are blocking and may never be skipped.
  • Role and permission resolution is data-driven and unit-tested; tier gating is enforced server-side, never by hiding UI.

4.2 Integrity rules

  • Constraints in the database, not just the app: foreign keys, not-null, unique, and check constraints encode the invariants. The application is not the last line of defence.
  • Immutable event data. The raw events table is append-only; corrections are new rows, never edits. Aggregates are derived and rebuildable from raw.
  • Audit log on every sensitive mutation: who, what, when, before/after, trace ID. Admin and billing actions always. Append-only.
  • Backups & restore: automated backups plus point-in-time recovery. A restore drill is performed once per phase and recorded — an untested backup is not a backup.
  • Retention is declared per table in the schema documentation, and enforced by a scheduled job.
05

The configurator contract

Document 03 defines the protocol. This section defines how we keep it from silently breaking once brands and models multiply. The configurator is built in-house, but it stays deliberately decoupled behind this versioned protocol — platform and render surface must be able to evolve, deploy, and fail independently.

The model, restated

The configurator is a TV screen; Autoverse is the remote control. We own every control, every CTA, every form, and all PII. It renders what it is told and reports back only what happens inside its own canvas. Commands out: init, set_option, apply_config, set_view, set_lighting, play_feature, request_snapshot, preload, reset. Signals in: ready + manifest, state_applied, loading, error, canvas_interaction, session, snapshot.

5.1 Hardening the contract Blocking

  • The protocol is versioned. Every message carries a protocol version. Autoverse refuses to initialise a configurator declaring an unsupported version and renders the fallback experience instead of a blank frame.
  • Origin is locked both ways. We validate the sender origin on every inbound message and target a specific origin on every outbound one. Never *. Unknown origins are dropped and logged.
  • Every inbound signal is schema-validated before it reaches application code. Malformed messages are dropped, counted, and alerted on — never trusted.
  • Manifest drift is a monitored failure. Our CMS is the source of truth for the option vocabulary. On ready, we diff the configurator's manifest against our catalogue; any mismatch raises a drift alert naming the model and the offending option IDs, and disables the affected controls rather than sending commands that will fail.
  • Every command has a deadline. If state_applied does not arrive within the budget, we log a timeout with the model and command, surface a non-blocking notice, and keep the UI responsive.
  • Contract tests run in CI against a mock configurator implementing the spec — covering handshake, each command, each signal, malformed input, wrong origin, wrong version, and timeout. The bridge is never tested only by hand.

5.2 Degraded modes

Failure User sees System does
Iframe fails to load Static gallery of the model, controls hidden Log + alert on rate; page fully usable, CTAs intact
No ready within budget Fallback imagery, "3D view unavailable" notice Timeout logged with model ID; retry once
Manifest drift Affected options hidden, rest of the configurator works Drift alert to Slack naming model + options
Pixel-stream session unavailable Light configurator remains; 360 entry disabled with reason Session failure logged; capacity signal tracked
Configurator errors mid-session Last good state retained; no blank canvas error signal captured with context

The rule: the model page must remain useful — specs readable, CTAs working, lead capture functional — with the configurator entirely absent. Lead capture never depends on 3D.

06

Event pipeline & delivery guarantees

"Capture every possible data bit" is only credible if we can prove nothing was dropped. This is how the data layer earns that claim.

6.1 The path an event takes

Ingest path
  control click / canvas signal / page view
        │  (client buffers; batches; survives navigation via sendBeacon)
        ▼
  event envelope  { event_id(uuid v4) · schema_version · brand_id · model_id
                     session_id · trace_id · occurred_at · payload }
        ▼
  Edge Function ingest ── validate schema ── rate limit ── stamp received_at
        │                      │                                │
        │ reject ──────────────┴──> counted + logged (never silently dropped)
        ▼
  events table  ── append-only ── UNIQUE(event_id) = idempotent retry
        │
        ├──> scheduled rollups ──> aggregated views (dashboards read these)
        └──> failures ──> dead-letter table ──> alert + replay tool

6.2 The guarantees Blocking

  • Idempotency. Every event carries a client-generated event_id; the table enforces uniqueness. Retries are therefore always safe and never double-count.
  • At-least-once delivery. Clients retry with exponential backoff; unsent batches persist across page navigation. Combined with idempotency this yields effectively-once storage.
  • Nothing is dropped silently. A rejected event is written to the dead-letter table with its reason. An empty DLQ is a monitored condition; entries raise an alert.
  • Daily reconciliation. A scheduled job compares emitted counts (client-side counters) against persisted counts per brand and model, and posts a gap report to Slack. A gap above threshold is an incident.
  • Schema versioning. Every event type has a versioned schema in the shared types package — one source of truth for producer, validator, and consumer. Adding an event without registering its schema fails the build.
  • Aggregates are rebuildable. Rollups can be recomputed from raw events at any time. Dashboards never read a number that cannot be reconstructed.
  • Leads are stricter than events. A lead write is synchronous and acknowledged; failure is shown to the user with a retry, never swallowed. Any lead in the DLQ is a zero-tolerance, immediate alert.
  • Consent-aware. Analytics respect the consumer's consent state; PII never enters the events table — leads are a separate, access-controlled entity.
07

The observability standard

"Absence of logs" is treated here as a defect class, not an oversight. This section is the instrumentation contract every feature is built against.

7.1 The logging contract Blocking

  • Structured JSON only. No free-text logging. Every line carries: timestamp, level, service, env, trace_id, brand_id (where applicable), event, duration_ms, outcome.
  • One trace ID, end to end. Generated at the edge, propagated through every call, returned in response headers, and attached to client errors — so any user report resolves to a single trace.
  • Every boundary crossing is logged at entry and exit with an outcome: HTTP handlers, Edge Functions, database mutations, scheduled jobs, and every configurator message.
  • Every catch block either handles or re-raises — and always logs. A swallowed exception is a review failure. An empty catch is a merge blocker.
  • No PII in logs, ever. Names, emails, phone numbers and identifiers are redacted at the logger, not by convention. A log-scrubbing test asserts this against known PII patterns.
  • Correlation with product analytics: PostHog for behaviour, Sentry for errors and performance, structured logs for system truth — all joined by trace and session ID.

7.2 What must be instrumented before a feature is done

Signal type Required for every feature
Logs Entry/exit of each boundary, all errors with context, all rejected input
Metrics Request rate, error rate, latency (p50/p95/p99), and one business counter
Traces The full path of the flow, including database and external calls
Product events The user-visible actions the feature introduces, with a registered schema
Alerts At least one condition that would tell us this feature is failing in production
The observability test

Before a feature is marked done, answer this: if this breaks at 3am for one brand only, would our telemetry alone tell us what happened, for whom, and why? If the answer is no, the feature is not done — regardless of whether the code works.

08

SLOs, alerts & on-call

Objectives are deliberately few and defensible by one engineer. Alert on symptoms users feel, not on every anomaly — noisy alerting is how real failures get missed.

Service level objective Target Alert when
Public site availability 99.9% monthly Error rate breaches budget over a rolling window
Model page LCP (p75, mobile) Under 2.5s Sustained regression beyond budget
Lead submission success 99.9% Any failed lead — page immediately
Event ingest success 99.5% DLQ entries appear, or reconciliation gap exceeds threshold
Dashboard query latency (p95) Under 1.5s Sustained breach — signals aggregate strategy is failing
Configurator ready rate 99% of sessions Ready failures spike for any single model

8.1 Alert discipline

  • Three severities. Page (revenue or data loss — leads failing, tenant isolation anomaly, site down). Notify (degradation — configurator errors, drift, DLQ, budget burn). Digest (trends, cost, weekly rollup).
  • Every alert names its runbook. An alert with no documented response is deleted or given one — no exceptions.
  • Alert fatigue is a tracked defect. Any alert that fires without action twice is tuned or removed at the next review.
  • Slack is the single pane: deploys, CI failures, alerts, drift reports, reconciliation gaps, cost rollups, weekly digest — separate channels by severity so the noisy ones never bury the urgent ones.
09

Environments & release pipeline

9.1 Environments

Local

Development

Supabase local or a dedicated branch. Never pointed at production data.

Preview

Per-PR staging

Vercel preview + Supabase branch. Every change is QA-able at a real URL with real migrations applied.

Production

Live

Deployed only from main, only after all gates pass. Exposure controlled by flags, independent of deploy.

9.2 Release sequence Blocking

Every change, no exceptions
  spec ─> branch ─> build behind flag ─> self-gate (lint · types · tests · secret-scan)
       ─> subagent review (code-reviewer + security-review)
       ─> PR ─> full CI gate suite ─> preview deploy + migration on branch DB
       ─> QA on preview URL ─> merge to main
       ─> production deploy + migration ─> smoke tests against production
       ─> flag enabled progressively ─> monitor burn ─> docs entry ─> Slack notify

9.3 Migration safety

  • Expand → migrate → contract. Never a destructive change in the same release as the code that depends on it. Add the new shape, backfill, switch, then remove — separate releases.
  • Every migration is reversible or has a documented recovery path. Irreversible migrations require an explicit written decision and a fresh backup verified beforehand.
  • Migrations run on a staging branch first, always, and are reviewed by the security-review subagent for RLS coverage.
  • Rollback is rehearsed, not theorised. Vercel instant rollback for code; flags for behaviour; a documented database recovery path. Drilled once per phase.

9.4 Post-deploy verification

A deploy is not complete when it finishes — it is complete when it is verified. Production smoke tests run automatically after every deploy against the critical flows in §11. A failed smoke test triggers automatic rollback and a page.

11.2 The pyramid

  • Unit (Vitest) — business logic, permission and tier resolution, billing state machine, data-layer functions, event schema validation.
  • Integration — API routes, Edge Functions, and RLS behaviour against a real database branch. This layer is the backbone of the confidentiality claim.
  • Contract — the configurator bridge against a spec-compliant mock, including every failure mode.
  • End-to-end (Playwright) — the inventory above, run in CI and as production smoke tests after deploy.
  • Accessibility — axe across every Storybook story, both surface themes, both text directions, and reduced-motion.

  • Visual regression Tracked — Chromatic once components stabilise.

Coverage rule: we do not chase a global percentage. We require that every entry in the flow inventory, every permission branch, and every error path in the ingest pipeline is covered — and we treat an untested error path as an untested feature.

12

Failure handling & degradation

Every external call is assumed to fail eventually. The architecture's job is to make that boring.

12.1 Standing rules Blocking

  • No call without a timeout. An unbounded call is a merge blocker.
  • Retries only where safe. Idempotent operations retry with exponential backoff and jitter; non-idempotent ones fail fast and surface.
  • Circuit-break repeat offenders. A dependency failing consistently is bypassed to its degraded mode rather than retried into the ground.
  • Errors are typed and boundaried. Every surface has error boundaries; users see an actionable message, never a stack trace or a blank screen.
  • Never fail a page for a non-essential dependency. Analytics, snapshots, and recommendations degrade silently; specs, CTAs, and lead capture never do.

12.2 Degradation matrix

Dependency down Degraded behaviour Severity
Configurator / pixel stream Static gallery; all specs and CTAs intact Notify
Analytics ingest Client buffers and retries; browsing unaffected Notify
Lead write User sees explicit failure + retry; DLQ + immediate page Page
Auth provider Public browsing continues; accounts and dashboards unavailable with clear notice Page
Database read (dashboards) Cached aggregate served with a staleness indicator Notify
CMS content missing Model omitted from listings rather than rendered broken Notify
13

Feature flags & progressive delivery

  • Every user-facing change ships behind a flag, default off. Deploy and release are separate events.
  • Flags are data, managed in the admin portal, scoped globally, per brand, or per tier — the same mechanism that powers tier gating.
  • Enforcement is server-side. A flag that only hides UI is not a flag; the API refuses the call too.
  • Every flag has an owner, a purpose, and an expiry date. Stale flags are removed at each phase boundary — flag debt is tracked like code debt.
  • The kill path is tested. Turning a flag off must fully remove the feature with no deploy and no residue. Verified when the flag is created, not when it is needed.
  • Progressive exposure: internal → one pilot brand → all brands, watching error budget between steps.
14

Security & confidentiality

  • Isolation: RLS at the database with mandatory cross-tenant tests; least-privilege RBAC; tier gating enforced server-side.
  • Secrets: environment config only; secret-scanning hook blocks commits; keys rotated on any suspicion; service role never in a client runtime.
  • PII: minimised, never in URLs or logs, encrypted in transit and at rest, visible only to the owning brand and authorised staff. Retention declared and enforced.
  • Input: validated at every boundary with schemas; parameterised queries only; output escaped by default.
  • Embeds: sandboxed iframes, origin-locked postMessage both directions, strict content security policy, no keys crossing the boundary.
  • Audit: append-only log of sensitive changes with actor, trace, and before/after.
  • Dependencies: automated vulnerability scanning in CI; a critical advisory blocks release.
  • Client-facing posture Tracked — a data processing agreement, security whitepaper, and data-flow diagram, with SOC 2 / ISO 27001 as the maturity path. Distinguish clearly between what we will not do (contractual, audited) and what we cannot do (technical). Regulatory position for Egypt to be confirmed with counsel.

16

Design system & motion

The neutral monochrome system is locked: Mist canvas, Onyx ink, Gunmetal surfaces, Slate, Platinum — no chromatic accent, so brand colour and the car itself carry all colour. Google Sans Flex and Cairo, both under the open font licence, self-hosted, with automatic switching for Arabic and right-to-left.

  • Contrast is structural. Every surface token is paired with its required foreground; a component on a dark surface sets its own text colour. An invariant test rejects any unpaired surface, and axe verifies every rendered story. Dark-on-dark is made unrepresentable rather than merely forbidden.
  • Storybook is the source of truth for the component library, documented and testable, with surface, direction, and reduced-motion toggles.
  • Motion is a system, not decoration. Tokenised durations, easings and springs; a semantic layer that names motions by purpose so components never improvise; reduced-motion enforced as a blocking gate exactly like contrast. Motion must guide attention, communicate state, or preserve spatial continuity — otherwise it is removed.
  • Responsiveness outranks smoothness. No animation may compete with the configurator render or delay input.
17

Runbooks & incident response

17.1 Required runbooks Blocking

Each is a short document: symptom, how to confirm, immediate mitigation, root-cause path, and how to verify recovery.

  • Site down or deploy failed · rollback procedure
  • Lead submission failing · DLQ inspection and replay
  • Event ingest gap detected · reconciliation and backfill
  • Configurator not loading for a model · drift, version, or origin diagnosis
  • Suspected cross-tenant exposure · containment first, then investigation
  • Database restore from backup
  • Secret leaked · rotation sequence
  • Cost spike · identification and throttle

17.2 Incident procedure

  1. Declare. Post in the incident channel with severity — declaring early is always correct.
  2. Mitigate before diagnosing. Flag off, roll back, or degrade. Restore service first.
  3. Communicate to affected brands if their data or service was involved, within the committed window.
  4. Resolve and verify with telemetry, not assumption.
  5. Write it up within 48 hours — blameless: timeline, cause, why our gates missed it, and the specific new gate or test that would catch it. Every incident ends by strengthening the wall.

Definition of Done

A feature is done only when every line is true

Spec met · types strict, no unjustified any · unit + integration tests pass · RLS policy present and isolation test proving it · every critical flow it touches covered E2E · structured logging at every boundary · metrics and at least one alert defined · product events registered with schemas · error paths handled with timeouts and a degraded mode · lint and format clean · performance budget met · contrast AA and reduced-motion respected · behind a flag with a verified kill path · docs entry written · runbook updated if it introduces a new failure mode · Slack notified.

The code-reviewer and security-review subagents check every diff against this list before merge. A feature that works but is unobserved, untested, or unflagged is not done — it is a liability that happens to function today.

19

Roadmap & production gates

Phase 1 delivers the engine and its five applications, proven end to end with one brand and one model in full production hardening, with multi-tenant and multi-market structure built in from the first migration. Each sub-phase ends at a production gate — a specific, demonstrable condition. A phase is not complete because its features exist; it is complete when its gate is passed.

Phase 1·A

Engine core

Tenancy spine with markets and entitlements as first-class entities; structured asset bucket with checksum discipline; job queue; ingest and lead pipeline with DLQ and reconciliation; flags; audit.

Gate Isolation suite green; an event and a lead survive an induced failure and reconcile to zero gap.
Phase 1·B

Risk register

Tracked openly and reviewed at every phase boundary. A risk with no owner and no mitigation date is escalated.

Risk Impact Mitigation
Model delivery contract and shared vocabulary not locked with the studio Blocks the pipeline at its entry point; naming drift breaks automation per model Deliver the Model Delivery Spec and manifest template; agree the shared ID list and its change process in writing
Option vocabulary drift between CMS, manifests and configurator Broken controls, silently, per model Manifest diff on every handshake with alerting; CMS as sole source of truth
Pixel-streaming hosting concentration Per-session economics and regional latency set the configurator's unit cost; incumbent publishes no SLA Decided: incumbent flat-rate provider for launch (Europe zone suits Egypt routing); regional provider adopted at Gulf expansion; re-evaluate self-hosting near ~50 sustained concurrent streams; no published SLA — accepted as a known risk on the basis of an established vendor relationship, to be revisited if client contracts carry uptime commitments; fallback provider kept configured; session lifecycle designed provider-agnostic
Render farm as a single hardware dependency Pipeline stalls if farm hardware is down or output drifts from the declared matrix Queue with stall alerts; expected-vs-present verification; failed-frame retry; no studio dependency at serve time
AI content quality below brand standard Brochures blocked or brand trust damaged Human approval gate on every asset; brochure renders without content blocks; prompt set versioned and improvable
Delivery timeline compression Fixed 45-day window against full production hardening Scope is cut, gates never; one brand one model end-to-end defines done; Later items documented in place
Single-engineer bus factor No second pair of eyes on any change The merge wall, project memory, runbooks, and documentation as the compensating control
Alert fatigue masking a real failure A genuine incident goes unnoticed Three severities, separate channels, mandatory tuning review
Aggregate query cost at scale Dashboard latency breach; database pressure Materialised views, scheduled rollups, p95 latency SLO as early warning
Client data-confidentiality demands exceeding current posture Lost or delayed enterprise deals Layered posture with an honest will-not versus cannot distinction; compliance path defined
