00

How to read this document

This is a flow-confirmation artifact, not visual design. Boxes show what exists on each screen and how it groups — not where it finally sits. Position, size and order in these wireframes are illustrative only (in the showroom, search and filters need not sit side by side on top); real placement, hierarchy and composition are decided at the high-fidelity design step, per page, on the locked design system. Numbered markers 1 explain the intent beneath each wireframe. The locked design language (monochrome system, car carries the colour, controls on solid surfaces) applies to everything here but is deliberately not rendered — approving flow and approving pixels are two different decisions and we take them in that order.

Read it as three loops: the consumer journey (§2–§6), the admin production pipeline that manufactures that journey (§7–§8), and the brand dashboard that monetises its data (§9). §10 maps what we capture at every step, §12 shows what each screen does when something fails, and §13 is the list of things you are actually approving.

What this blueprint assumes (locked upstream)

Nmesis (studio) creates and delivers 3D models; everything from the upload event onward — rendering on the in-house Unreal farm, the configurator, content, data, hosting — is this system. The engine’s pipeline is triggered by a 3D file landing in the structured asset store; rendering runs on the in-house Unreal farm via a job the engine queues, watches, and reports progress on. Assets live in a structured S3/R2 file system. Configurator is the mandatory base SKU. Data is always collected in full; visibility is tier-gated. Production doctrine v2.0 applies without exception.

01

The journey at a glance

Two pipelines meet in the middle. The admin pipeline manufactures the experience; the consumer journey walks through it; every step of the walk feeds the data layer that the brand dashboard and, later, Autoverse itself are built on.

Admin pipeline

Upload detected → render → configurator ready → content → approval → data fill → publish

→
Consumer journey

Showroom → Brochure (per trim) → Configurator → CTA / lead

→
Data layer

Every event captured → leads scored per brand → dashboard views → (later) Autoverse

The consumer journey is deliberately a funnel with three depths: browse (showroom — low commitment, many models), consider (brochure — one trim, rich content, light configurator), desire (configurator — live Unreal session, personal build, CTAs). Each step down the funnel is a higher-intent signal, which is exactly what lead scoring will weight.

02

Brand URLs & journey entry

  • One URL per brand per market, e.g. {brand}.engine-domain.com/{market} — subdomain now, custom domain (their own) as a Later upgrade. Market sets currency, language (incl. Arabic/RTL), and consent defaults.
  • The URL exposes only what the brand bought. Showroom tier → entry is the showroom. Brochure+configurator only → entry is the model's brochure. Configurator only → entry is the configurator page itself. Same engine, same data capture, different front doors.
  • Every entry carries attribution: UTM/source captured on first touch and attached to the session — the lead's origin story starts here.

06

The CTA & lead layer

CTAs appear on all three screens but always resolve to the same engine-owned lead flow — one pipeline, one schema, wherever the journey converts.

CTA tap

Any screen · context attached: brand, model, trim, current build, session

→
Lead form

Minimal fields + consent checkbox (market-specific wording) · WhatsApp deep-links with prefilled context

→
Engine lead record

Synchronous, acknowledged write · full journey history attached · DLQ + page on any failure

→
Routing

Brand dashboard (tier permitting) · notification to brand · scoring queue

  • A lead is never just a form fill — it carries the entire journey behind it: models viewed, trims compared, colours tried, time in configurator, shared builds. That history is what scoring consumes and what makes the lead worth paying for.
  • Consent is captured at the form, per market, stored with the lead. Wording per market comes from counsel; resale consent is a separate, Later checkbox — documented in the lead schema now.

Admin — the production pipeline App 5

The pipeline board is the heart of the admin portal: every model for every brand is a card moving left to right, and the engine automates every hand-off it can see. The pipeline begins when a 3D file lands in the structured bucket. Everything upstream of that moment is studio work outside this system’s scope; the upload event is the trigger, and the delivered manifest’s variant declarations (trims, exterior and interior colours) define the expected render matrix the engine verifies against.

10

Data capture map — everything, everywhere

The concrete answer to "literally everything the user did." Every event follows the envelope and delivery guarantees of the production plan (idempotent, at-least-once, DLQ, daily reconciliation). Time-on-everything comes from paired enter/leave events, so duration is derived, not guessed.

Journey stepCaptured events (each with full context: brand · market · model · trim · session · source)
Entrypage_view · source/UTM attribution · language · device · consent state
Showroomfilter_applied (which, value) · search_query · model_group_viewed (enter/leave) · trim_card_viewed · trim_card_cta (view/configure)
Brochuretrim_switched (from→to) · content_block_viewed (enter/leave) · video_play/progress/complete · light_config_swatch (colour, dwell) · light_config_view_toggle · specs_table_opened · recommendation_clicked
Configuratorsession_requested/queued/started/ended (duration, cost) · every control touch: colour_selected, interior_selected, view_changed, lighting_changed, feature_played · canvas_interaction (spin/zoom from the signal channel) · build_shared · shared_build_opened
Conversioncta_viewed · cta_clicked (which, where) · lead_form_opened/field_completed/abandoned/submitted · whatsapp_deeplink_opened
Systemconfigurator_error/timeout · degraded_mode_shown · perf samples — failures are data too

Colour affinity ("which colour did he try most") is a query over colour_selected events, not a special feature — which is the point: capture atomically, aggregate freely, and every future question is answerable without new instrumentation.

Confirmation checklist — what you are approving

Approve, amend, or strike each. When this list is clean, the three consumer pages go to high-fidelity and the engine + admin specs go to Claude Code.

  1. The funnel shape — showroom → brochure → configurator as three depths, with the two exits per trim card (§3.4).
  2. Brochure owns the light configurator; configurator page owns the Unreal session — no streaming on the brochure (§4.2, §5).
  3. Trim switching in place on the brochure rather than separate pages per trim (§4.1).
  4. AI content is brochure-first, approval-gated, conditioned on renders (not fine-tuned) with per-model LoRA as Later (§8.1).
  5. The 7-stage pipeline board (upload → publish) and folder-computed render progress (§7).
  6. CTA set per brand — Share build · Test drive · Contact seller · WhatsApp — configurable from both dashboard and admin (§5.3).
  7. Brand URL model — subdomain per brand per market now; custom domains Later (§2).
  8. Packaging matrix as in §11, entitlements and tiers as separate flag axes.
  9. The event taxonomy of §10 as the capture baseline (additions welcome; removals discouraged).
  10. Degraded journeys of §12, in particular: conversion never waits for a GPU.
