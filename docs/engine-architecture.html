The Engine · Architecture Reference · v3.0

One engine. Every product built on it.

The Engine is the shared infrastructure layer beneath everything Autoverse ships: the data, the assets, the pipeline, the security, and the guarantees. This document is the system reference — what exists, where the boundaries are, and how the pieces fit.

00

Names, and how to read this

Two names, kept precise throughout: Autoverse is the company — and also the name of the consumer platform product the company will build in a later phase, in its own repository. The Engine is the infrastructure layer this document describes, living in the autoverse-engine repository. It deliberately has no product name: it is not a product, it is the layer every product stands on. When this document says "the platform," it means the Engine plus the applications running on it today.

This is the reference for what the system is. Its two siblings govern how it is run (the Production Plan — guarantees, gates, observability, failure handling; it wins any conflict) and what the experience is (the Journey Blueprint — approved screens, flows, and events). §15 maps the full set.

01

What the Engine is

The Engine is the layer that makes every product possible and no product in particular: hosting, the structured asset store, the data core, tenancy and security, event ingestion, leads, content, entitlements and tiers, jobs, and the integration surface. Applications are thin by design — they render experiences and capture interactions; everything durable lives in the engine.

The division of labor with the studio is a single clean line: Nmesis creates and delivers 3D models; everything from the upload event onward is the Engine — rendering on the in-house Unreal farm, the configurator, content generation, publishing, data, and monetization. The delivery contract (two files: the model and its manifest) is specified in the Model Delivery Spec; nothing upstream of that handover is modeled here.

Phase 1

The engine + three apps

The Engine itself, plus the consumer app (three gated surfaces), the brand dashboard, and the admin portal — proven end-to-end with one brand, one model, production-hardened.

Phase 2

The Autoverse platform

The multi-brand consumer product, built on the data and content the Engine accumulates — a separate repository consuming the same engine.

Beyond

Any future app

New products plug into the same data core, asset store, entitlements, and guarantees — the engine is the moat; apps are interchangeable.

02

Commercial model

  • The Configurator is the base SKU. Every deal includes it; the Digital Brochure and Virtual Showroom attach to it and are never sold alone.
  • Two independent flag axes. Entitlements decide which consumer surfaces a brand's URL exposes. Tiers decide which dashboard modules the brand sees. Both are data, resolved server-side, changeable without deploys.
  • Capture is never gated. Every brand generates full data from day one regardless of tier; upgrading reveals history retroactively — the product's strongest built-in upsell.
  • Markets are first-class. A brand operates per market (currency, language and direction, consent defaults, pricing); one brand may run several markets, each with its own URL. MENA first, structurally global.
  • Brand URLs: one per brand per market, subdomain-based; custom domains are a later, additive feature.
  • Billing: operator-controlled free periods per brand, then subscription billing (manual invoicing first, gateway later). Every billing state transition is audit-logged.

04

Engine subsystems

Data core

Postgres + RLS

The keystone: row-level security is the tenancy boundary, delivering multi-tenancy, RBAC, and confidentiality at the layer no application bug can bypass. Every brand-scoped table carries its policy from birth; constraints live in the database; raw events are append-only; aggregates are derived and rebuildable.

Asset store

Structured object storage

The single home of 3D deliveries, rendered multiples, and generated content. Content-hashed immutable paths, checksums at write, versions never overwritten. Serving is CDN-cached; the store's layout (§07) is what makes page generation automatic.

Ingest

Event pipeline

Validated, rate-limited edge ingestion; idempotent event IDs; at-least-once delivery with client buffering; dead-letter queue; daily reconciliation. Nothing is dropped silently — the analytics product stands on this claim.

Leads

Stricter than events

Synchronous, acknowledged writes; failures surface to the user and page the operator. A lead carries its entire journey history — the data that makes it scoreable and sellable-quality.

Jobs

Queue + orchestrators

Render jobs, generation jobs, rollups, retention enforcement — all queued, stateful, observable, with stall detection. The upload-watcher turns a studio delivery into a pipeline run.

Control

Entitlements · tiers · flags

One flag mechanism powers feature rollout, surface entitlements, and tier gating — data-driven, server-enforced, kill-path-tested, auditable.

05

The applications

5.1 apps/consumer — one app, three gated surfaces

The Showroom, Brochure, and Configurator are one application because they are one journey: one session, one analytics trail, one attribution chain from first touch to lead. Entitlement flags decide which routes a brand's URL exposes; disabled surfaces simply don't exist for that brand. Splitting them into separate apps would fragment sessions exactly where the product's value — the unbroken journey record — is created.

  • Virtual Showroom — the brand's range: filterable, searchable models with trims beneath; each trim exits deeper (brochure) or straight to configuration.
  • Digital Brochure — one trim told richly: generated content and renders, in-place trim switching, the light configurator (instant pre-rendered image swapping, no streaming), specs, CTAs, same-brand recommendations.
  • Configurator — the streamed Unreal session in an iframe, wrapped in engine-owned controls, build summary, and CTAs (configurable per brand). Controls render from the engine's own option catalog and never wait on the stream; the page converts fully with the stream absent.

5.2 apps/dashboard — the brand product

Tenant-isolated by RLS, tier-gated by flags: overview, journey funnel, model and trim insights, leads with per-lead journey history and scoring, exports, settings (CTA configuration, notifications, team RBAC). Reads aggregates only. Locked modules are visible but inert — the upgrade path is part of the interface, and the server refuses locked data regardless.

5.3 apps/admin — the operator portal

The pipeline board (§06), catalogue management (brands, markets, models, options — the source-of-truth vocabulary), generated-content review, commercial control (tiers, subscriptions, free periods, finance), cross-brand analytics, leads oversight, ops (logs, jobs, DLQs, costs), staff RBAC, audit.

5.4 The configurator contract

The render surface is built in-house but stays deliberately decoupled behind a versioned message protocol (commands in: init, set_option, set_view, preload…; signals out: ready+manifest, state_applied, canvas_interaction, session…), origin-locked both ways, schema-validated, drift-checked against the catalog on every handshake. Platform and render surface must be able to evolve, deploy, and fail independently.

06

The production pipeline

The pipeline manufactures the consumer experience. It begins at the upload event and ends at publish; every stage is a state on the admin board, every transition logged, every failure loud.

1 · Upload

3D file + manifest.yaml detected; manifest validated against the shared vocabulary; operator notified. The manifest's declarations define the expected render matrix.

2 · Render

Operator starts the run; the farm renders trims × colors × interiors × views; progress = files present ÷ expected; stalls alert.

3 · Configurator ready

Matrix complete → configurator registered → protocol handshake verified.

4 · Content

Generation runs per trim (§07): images, video, copy — from versioned prompts, conditioned on this trim's renders.

5 · Approve

Human review of every generated asset and copy block; nothing unapproved can publish.

6 · Data fill

Specs, prices per market, filters, CTA configuration.

7 · Publish

Surfaces go live behind the brand's entitlement flags. Per-trim: a trim publishes only when complete; siblings unaffected.

07

Content generation

The brochure's hero imagery, its cinematic banner video, and the page copy are manufactured, not commissioned — generated per trim from the trim's own renders, so accuracy is inherited from the pipeline rather than hoped for. The design principle: renders are the identity; generation adds the world around them.

7.1 The three-stage chain

  • Images. An image model generates scene imagery conditioned on the trim's approved renders (image-to-image / reference-based): new environments, lighting, and moods around the actual car geometry. Inputs: the trim's hero renders + a fixed, versioned prompt set maintained in the admin (prompts are data — refining them upgrades every future model with zero code). Fixed count per trim.
  • Video. Approved generated images seed an image-to-video model to produce one or two short cinematic clips per trim, at the exact aspect ratios the brochure banner consumes. Approval sits between the stages by design: video is the expensive step, and it only ever runs on images a human has already accepted.
  • Copy. A text model generates the page's written content per brand × model × trim — headline, subcopy, feature blocks, specs framing — as structured blocks, not prose files, from the manifest, the filled specs, and a per-brand voice profile (tone, vocabulary, things never to say). Generated in every market language (English and Arabic from day one). Copy passes the same approval gate as imagery.

7.2 Provider strategy

  • One adapter, swappable providers. All generation flows through the engine's content-generation service, which speaks to managed model providers behind a single interface (submit job → poll/webhook → fetch asset). Model vendors in this space change monthly; the adapter makes the choice reversible and per-stage (the image provider, video provider, and text provider are independent decisions).
  • Selection criteria: API + webhook maturity, commercial usage rights over outputs, per-asset cost visibility, reference/image-conditioning quality on automotive subjects, and output-resolution ceilings. The current provider choices are recorded as ADRs, not in this document — the architecture outlives them.
  • Providers receive renders and prompts — never PII, never lead or analytics data.

7.3 Asset store layout — where everything lands

Naming convention (content-hashed serving paths derive from this) 
assets/{brand}/{model}/v{version}/
  source/                        ← the delivered 3D file + manifest.yaml
  renders/{trim}/{exterior}/{interior}/{view}.png
  content/{trim}/
    images/{promptset-v}/{prompt-id}-{seq}.jpg      ← generated stills
    videos/banner-{aspect}.mp4                      ← cinematic clips
    copy/{locale}.json                              ← structured text blocks
  • The layout is the automation: page generation reads this tree by convention — a brochure assembles itself from renders/, approved content/, and the filled catalog data, with zero manual placement.
  • Generation state lives in the database, assets in the store: every asset row tracks provider, prompt version, seed inputs, cost, and approval state (generated → approved | rejected | regenerating). The brochure can only reference approved.
  • Degradation: content blocks are optional by design — a brochure renders complete from renders + copy alone if generation is late, rejected, or down.
08

Data & leads

  • Capture everything, atomically. The journey emits fine-grained events (per the Blueprint's capture map): every filter, view, trim switch, swatch touch, configurator command, canvas interaction, session state, and CTA step — each with full context (brand, market, model, trim, session, source) and paired enter/leave events so every duration is derived, not guessed.
  • Questions are queries, not features. "Most-tried color," funnel drop-off, comparison patterns — all answerable from raw events without new instrumentation. Dashboards read scheduled aggregates; raw events remain the rebuildable source of truth.
  • Leads are the conversion product: a lead = contact + consent + the entire journey behind it. Scoring starts rules-based (weighted funnel-depth and engagement signals, per brand), with model-based scoring as a later, additive upgrade. Export for brands; operator oversight across brands.
  • Consent is captured at the form, per market, stored with the lead. Any future secondary use of lead data is gated on its own explicit consent and legal review — structurally separated from serving the brand.
  • The cross-brand view (operator only) is the compounding asset: market-level automotive interest data that no single brand sees — and the foundation the Phase-2 platform is built on.
09

Tenancy, security & confidentiality

  • Isolation is absolute and database-enforced: RLS on every brand-scoped table, deny-by-default, with mandatory cross-tenant tests that block any merge on failure. No brand can ever see another brand's data — proven, not promised.
  • Key discipline: the service-role key exists only in CI migrations and server-side jobs; browsers write only through validating edge functions; the iframe and generation providers receive no keys and no PII.
  • PII is minimized, never in logs or URLs, encrypted in transit and at rest, visible only to the owning brand and authorized staff; retention declared per table and enforced by schedule.
  • Everything sensitive is audited: append-only log with actor, trace, and before/after on admin, billing, and data-affecting actions.
  • Full mechanics, gates, SLOs, and incident procedure: the Production Plan. Client-facing posture (processing terms, security overview, compliance path): the client documentation portal (§10).
10

Integration surface & documentation

  • Outbound webhooks per brand: lead created, lead updated, threshold events — signed, retried, replayable.
  • Partner API (token-scoped per brand, tier-gated): read access to the brand's own leads and aggregates for CRM and martech integration. Same RLS guarantees apply to API tokens as to dashboard users.
  • Two documentation portals, one source: an internal portal (architecture, decisions, runbooks, data dictionary, how-and-why — the onboarding path for any future hire) and a client portal (security and confidentiality posture, webhook and API reference with auth and response shapes, what each tier includes). Both generated from the repo's docs so they cannot drift from reality.
11

Experience & design system

  • Quality bar: the consumer surfaces compete on feel — fast, precise, premium. Performance budgets are CI-enforced; the car, not the interface, carries the color.
  • The design system lives in code (design-tokens + ui, documented in Storybook): locked monochrome palette with a minimal semantic sub-palette for state feedback; structural surface↔foreground contrast pairing with an invariant test; self-hosted bilingual typography (Latin + Arabic, RTL-aware); Radix-based accessible primitives; a semantic motion layer with a restrained, precise character and reduced-motion enforced as a blocking gate.
  • Design workflow: the system is imported from this repository into the design tool; approved page designs return as locked specs; the same components implement them. One system, no drift, at every step from mockup to production.

14

Phases

  • Phase 1 — the Engine + the three applications, delivered through the Production Plan's sub-phases (engine core → pipeline & admin → consumer surfaces → dashboard & hardening), each closing at a demonstrable production gate. Done means: one brand, one model, the full journey, production-hardened, with multi-tenant and multi-market structure in place from the first migration.
  • Phase 2 — the Autoverse platform, its own repository on the engine's accumulated data — plus the deferred upgrades, each documented where it belongs: model-based lead scoring, checkout, secondary lead monetization (behind consent and legal), custom domains, per-model fine-tuned generation.
