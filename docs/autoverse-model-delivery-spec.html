Studio Handover · Model Delivery Spec · v2.0

Delivering a finished model takes two files.

When a car model is done, the handover is one folder containing the 3D file and a short manifest that describes it. That's everything — the moment it lands, the system takes over: rendering, the configurator, and the customer-facing pages all start from this delivery.

01

What this is, in one minute

Your work ends where the platform's work begins: a finished, agreed car model. This document describes the only interface between us — how that model is handed over. There is deliberately nothing else in it: no rendering settings, no configurator behaviour, no website details. Those are all handled on the platform side, automatically, starting from your upload.

Why so strict about the format? Because nobody is watching an inbox. A machine detects your delivery, reads the manifest, works out everything that needs to be produced, and notifies the team. If the delivery follows this spec, a model goes from your folder to a live, configurable car with zero back-and-forth. If it doesn't, the system stops and asks questions — which costs everyone a round-trip.

02

The handover

One delivery = one folder per model in the shared upload location (access details are provided separately, not in this document), containing exactly two things:

File 1

The 3D model file

The packaged model, in the format agreed with our rendering team (§03). One model per delivery — trims and colours are variants inside it, described by the manifest.

File 2

manifest.yaml

A short fill-in-the-blanks text file, from the template we provide, that tells the system what the model contains: its trims, exterior colours, and interiors (§04).

The one rule

A delivery without a manifest doesn't exist. The system only reacts when both files are present — the manifest is what turns a file in a folder into an instruction it can act on.

03

The 3D file

  • Format and packaging as agreed with the rendering team. The technical requirements (format, structure, naming inside the package) are settled directly between your artists and our rendering engineer and may evolve; this document doesn't restate them so it can't drift out of date.
  • One file per model. All trims and variants ship inside the one package; the manifest declares which ones exist.
  • The filename you upload must match the filename written in the manifest — that's how the system pairs them.
04

The manifest file

The manifest is the model's birth certificate. The system reads it and computes everything that must be produced — every trim × every exterior colour × every interior. Whatever is listed gets rendered and becomes choosable by customers. Whatever is not listed does not exist: it won't be rendered, won't appear in the configurator, and can't be sold. A filled example:

manifest.yaml — filled example (the template has instructions on every line)
brand: "brand-x"                  # IDs agreed with us — lowercase, dashes
model: "model-a"
model_display_name: "Model A"     # the name customers see
market_availability: ["EG"]

file:
  filename: "model-a_v3.zip"      # must match the uploaded file exactly
  version: 3                      # bump on every re-delivery (§06)

trims:
  - trim: "sport"
    trim_display_name: "Sport"
    exterior_colors: ["phantom-black", "glacier-silver", "carmine-red"]
    interiors: ["onyx-leather", "carbon-alcantara"]
  - trim: "gt"
    trim_display_name: "GT"
    exterior_colors: ["phantom-black", "chalk-white"]
    interiors: ["carbon-alcantara"]

Filling it takes minutes: copy the template, one block per trim, list the colour and interior IDs. That's the whole job.

05

The shared names

The IDs in the manifest — brand, model, trims, colours, interiors — come from one shared list we maintain together. Exact spelling, always: phantom-black, never "Black", "Phantom BLK", or "phantom black". The system matches names literally; to a machine, those are four different colours.

  • New colour or interior? It's added to the shared list first, then used in a manifest. A name the system doesn't recognise stops the delivery (§08) rather than guessing.
  • Why this matters so much: these same IDs drive the rendered image sets, the configurator options, the customer's saved builds, and the analytics brands pay for. One consistent name, end to end, is what keeps all of that automatic.
06

Updates & versions

  • Re-delivering the same model (fix, improvement, new variants): same folder, new file, and bump version in the manifest. Nothing is ever overwritten — every version is kept, and the platform switches to the new one only when its processing completes.
  • Adding a trim or colour to a live model is just a re-delivery: updated model file if needed, updated manifest listing the new variants, version bumped. The system works out what's new and produces only that.
  • Removing a variant: delete it from the manifest on the next delivery — it stops being offered to customers from then on.
07

What happens after you upload

So you know your delivery landed and what it triggers — all of this is automatic, none of it needs anything further from you:

  1. Detection. The system spots the new delivery, verifies both files are present and paired, and records it.
  2. Validation. The manifest is read and every ID is checked against the shared list.
  3. Team notification. The operations team is notified and starts the production run — rendering every combination the manifest declares.
  4. Live. Once processing and review complete, the model appears in the brand's configurator and pages. If anything is needed from the studio, you'll hear from us with specifics — silence means all is well.
08

If something's wrong

ProblemWhat happensThe fix
Manifest missingDelivery isn't processed — the system waitsAdd manifest.yaml to the folder
Filename in manifest ≠ uploaded fileDelivery flagged, processing stopsCorrect the filename line or the file name
Unknown colour / interior / trim IDDelivery flagged with the exact offending nameFix the spelling, or add the new ID to the shared list first, then re-deliver
Version not bumped on re-deliveryDelivery flagged as a duplicateIncrement version and re-upload the manifest

The principle: the system fails loudly and specifically, never silently. A flagged delivery names exactly what's wrong; nothing half-processes, and a mistake can never leak to customers.

09

Delivery checklist

Before you upload — two minutes

One folder per model · the 3D file, packaged as agreed · manifest.yaml filled from the template · filename matches the uploaded file · every ID from the shared list, exact spelling · version bumped if this is a re-delivery. Done — upload both, and the system takes it from there.
